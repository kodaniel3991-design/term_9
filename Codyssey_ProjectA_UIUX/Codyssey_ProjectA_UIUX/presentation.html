01 · 과제 요건

세 가지를 만들어야 한다

UI 디자인 이미지

3장 이상. 메인·목록·상세 등 역할이 구분되는 화면. 모바일 9:16 또는 데스크탑 16:9. 텍스트 깨짐이 수정된 상태.

작업 로그 문서

프롬프트 초안 → 수정 → 최종의 변천사. 각 단계에서 왜 바꿨고 결과가 어떻게 달라졌는지를 기록.

Figma 프로젝트

생성 이미지를 배치해 화면 흐름 구성. Hotspot 또는 화면 전환 표시가 있는 공유 링크.

평가의 무게중심은 이미지가 아니라 로그에 있다. 과제 목표 4개가 전부 "설명할 수 있어야 한다"로 서술되어 있기 때문이다.

02 · 기획

주제는 재미가 아니라 구조로 골랐다

  • 메인 → 목록 → 상세로 자연스럽게 분해되는가
  • 생성 모델이 잘 그리는 시각적 도메인인가
  • 텍스트 밀도가 후가공 가능한 수준인가
  • 스타일을 한 문장으로 정의할 수 있는가
  • 과제 예시(여행/항공권)와 겹치지 않는가

지도·대시보드·메신저는 제외했다. AI가 특히 못 그리거나 후가공 분량이 폭증하는 유형이다.

선정 — 반려동물 건강기록 앱

카드 UI 중심이라 생성 품질이 안정적이고, 기록 목록·상세라는 화면 역할 구분이 억지스럽지 않다. 텍스트 밀도도 후가공 가능한 범위에 들어온다.

03 · 워크플로우

한 화면에서 토큰을 완성한 뒤 나머지에 이식한다

기획 (화면 구조 · 데이터 설계) ↓ 스타일 토큰 설계 → 1개 화면으로 반복 검증 ················ 1~6차 ↓ 토큰 고정 → 나머지 화면 일괄 생성 ······················ 7~9차 ↓ 결함 식별 (텍스트 파손 + 논리 결함 + 비율) ↓ 후가공 (Figma 텍스트 · 도형 덮기) ↓ 프로토타입 조립 (Hotspot 연결)

4개 화면을 동시에 개선하면 변경 원인을 특정할 수 없고, 토큰이 바뀔 때마다 전량 재생성해야 한다. 홈 화면 하나에 6차수를 투입하고 나머지 3장을 각 1차수로 끝낸 것이 이 전략의 결과다.

04 · 1차 초안

4단어 프롬프트가 너무 잘 나왔다

pet health record app home screen, mobile UI, simple, clean

문제는 품질이 아니라 출처였다

  • UI 언어가 전부 영어 — "Buddy", "Sarah" 등 모델이 임의 생성
  • 하단 탭이 기획한 4화면 구조와 불일치
  • 텍스트가 한 글자도 안 깨져 후가공 재료 없음
  • 가장자리에 투명 배경 잔존, Age 칸 정렬 붕괴
  • 그래프에 축·눈금 없음 (장식용 선)

추상적 프롬프트는 결과를 모델의 평균값으로 수렴시킨다. 완성도가 높다는 것이 곧 기획 반영을 뜻하지 않는다.

05 · 2차 수정

한글화하고 기획 구조를 명시했다

변경 이유

  • 한국 사용자 서비스인데 UI가 영어인 것은 기획과 어긋남
  • 탭 구조를 기획한 4화면과 일치시켜야 프로토타입 연결 가능
  • 한글은 렌더링 난도가 높아 후가공 재료 확보를 겸함
  • 스타일을 텍스트 토큰으로 고정해 일관성 확보 준비

해결됨

한글 UI 전환 · 탭 구조 일치 · 투명 배경 제거

새 문제

장식 과다(배너 하나에 아이콘 4개) · 위계 역전 · 정렬 깨짐 · 날짜 부재

지정한 토큰(베이지+세이지+20px 라운드) 자체가 2021~22년 웰니스 앱 트렌드여서 결과물이 시대에 뒤처져 보였다.

06 · 3차 수정

장식을 빼고 데이터를 키웠다

적용내용
색 축소뉴트럴 베이스 + 액센트 1색
타이포 대비숫자는 크게, 라벨은 작게, 중간 크기 제거
경계 제거테두리·그림자 대신 여백으로 구분
데이터화장식 아이콘 자리를 스파크라인으로 대체

기록 행에 날짜가 추가되며 기록 앱으로서의 정보 구조가 성립했다. 그러나 2026 design trend 같은 추상적 트렌드 지시어는 결과에 유의미한 영향을 주지 않았다. 이 의문이 다음 차수의 실험 설계로 이어졌다.

07 · 4차 통제 실험

페르소나 기법은 이미지 모델에도 작동하는가

LLM 프롬프트 엔지니어링에서 널리 쓰이는 역할 부여가 이미지 생성 모델에서도 동일하게 작동하는지 확인하기 위한 실험이다.

설계

  • 콘텐츠 블록을 완전히 동일하게 고정
  • 스타일 지시부만 두 갈래로 분기
  • 다른 변수가 통제되므로 차이의 원인을 스타일 지시부로 특정 가능

4-A · 페르소나 + 추상 요청

You are a senior product designer at a world-class design studio, known for award-winning mobile interfaces. Design the most visually striking, sophisticated, cutting-edge screen possible for 2026.

4-B · 구체적 시각 어휘

Dark base #0D0F0E, noise grain Bento grid layout, 8px gutters Frosted glass cards, inner glow Accent gradient lime → teal Oversized display numerals Floating pill bottom navigation
08 · 4차 결과

스타일을 움직인 것은 페르소나가 아니었다

09 · 4-B 기각

화려함을 얻고 신뢰를 잃었다

결함내용
데이터 왜곡실제 3.9→4.2(약 7% 증가)인데 시각적으로 2배 이상 증가한 곡선
타이포 파손"4주 전"에서 숫자만 거대 — 의도가 아닌 렌더링 사고
액센트 남용그라데이션이 카드 4개 전부에 적용 — 강조가 없는 것과 동일
톤 불일치라임 네온은 피트니스·크립토 계열 색상 관습
가독성어두운 배경 위 저채도 회색 텍스트의 대비 부족

건강기록 앱은 숫자를 읽는 앱이지 보여주는 앱이 아니다. 용도와 스타일이 어긋났다.

10 · 핵심 발견 ①
이미지 생성 모델에서 페르소나 부여는 시각 스타일을 이동시키지 못한다.
스타일을 움직이는 것은 구체적 시각 어휘(명사)다.

왜 그런가

페르소나는 텍스트 모델에서 출력 분포를 이동시킨다. 그러나 이미지 모델은 프롬프트를 시각 요소로 해석하므로 "expert", "award-winning"은 그릴 대상이 없는 단어다.

실무적 함의

LLM 프롬프트 기법이 이미지 모델에 그대로 이전된다고 가정해서는 안 된다. 스타일 통제가 목적이라면 "세련되게"가 아니라 "다크 베이스 + 벤토 그리드 + 프로스티드 글래스"처럼 그릴 수 있는 명사로 번역해야 한다.

다만 페르소나가 무용하지는 않았다. 스타일이 아닌 완성도(정보 설계의 정교화)에는 분명히 작용했다.

11 · 5차 확정

A 계열로 회귀하고 정합성을 고쳤다

수정이유
배지 방향하락(↓0.1kg) 표시인데 그래프는 상승 추세 — 서로 모순
y축 범위3.8~4.6 → 3.8~4.4. 점이 눈금선에 정확히 안착
칩 색상접종=녹색, 병원=핑크, 투약=파랑 → 단일 녹색 계열로 통일

한글 파손 발생

기록 마지막 행이 체중 → 체종으로 렌더링됐다. 3차에서는 정상이었던 단어가 재생성 과정에서 변형됐다.

12 · 6차 최종

레이아웃은 그대로, 색만 바꿨다

전환 근거

국내 금융·의료·공공 서비스 앱의 주조색이 청색 계열에 집중되어 있어, 사용자가 "기록·검증·공적 신뢰" 맥락과 청색을 연결해 학습한 상태로 판단했다. 건강기록은 수의사 제출·보험 청구 등 대외 신뢰가 요구되는 데이터를 다루므로 이 관습을 따랐다.

실험적 가치

콘텐츠와 레이아웃 지시를 한 글자도 바꾸지 않고 색상 토큰만 교체했다. 다른 변수가 통제되었으므로 5차와 6차의 차이는 전적으로 색상에서 기인한다.

부수 효과 — 기록 행에 진입 화살표가 추가되어 상세 화면 연결 신호가 발생했다. 프로토타입 Hotspot 위치와 정확히 일치한다.

13 · 핵심 발견 ②

한글 파손이 저절로 복구됐다

3차 정상 → 4·5차 파손 → 6차 복구

프롬프트의 텍스트 관련 지시는 전혀 바꾸지 않았다. 그런데 결과가 달라졌다.

한글 렌더링 정확도는 프롬프트가 아니라 재생성 시점의 확률에 좌우된다.

따라서 프롬프트로 텍스트를 통제하려는 시도는 비효율적이며, 후가공 단계에서 확정하는 것이 올바른 워크플로우다. 8·9차에서 텍스트 밀도가 가장 높았음에도 파손이 0건이었던 것이 이를 뒷받침한다 — 밀도와 파손률은 비례하지 않았다.

14 · 일관성 전략

스타일 토큰을 문자열 단위로 복사했다

Style tokens (identical across all screens): - Background #F2F5F9 cool off-white - Card surface #FFFFFF - Primary accent deep navy #14386E - Secondary tint #E9EFF8 for chips - Text #16181D, secondary gray #737B87 - Card radius 20px, hairline border #DFE5EE - Serif display numerals for metrics, sans-serif for all Korean labels - Category chips: pill, tinted, navy text - Bottom nav 4 tabs, center FAB in navy - Thin single-weight line icons - Mobile 9:16, no device frame, opaque bg

시드 고정을 쓰지 않은 이유

GPT Image는 시드 값 직접 지정을 지원하지 않는다. 그러나 두 방식은 애초에 목적이 다르다.

방식유효한 상황
시드 고정같은 화면을 다시 뽑을 때. 동일 프롬프트 → 동일 결과 재현
토큰 고정다른 콘텐츠에 같은 스타일을 이식할 때

본 과제는 서로 다른 4개 화면을 같은 톤으로 묶는 것이 목적이므로, 토큰 고정이 목적에 부합한다. 시드 고정은 콘텐츠가 바뀌면 스타일 이전을 보장하지 않는다.

15 · 최종 산출물

토큰 하나로 네 화면을 묶었다

7~9차는 확정된 토큰 블록을 그대로 붙이고 콘텐츠 블록만 교체했다. 이미지 레퍼런스 없이 텍스트 토큰만으로 색상·카드 형태·칩·아이콘·내비 구조가 일관되게 유지됐다.

16 · 통제의 경계

통제된 것과 통제되지 않은 것

토큰으로 통제됨 — 정적 스타일

  • 색상 팔레트 — 4화면 동일
  • 카드 형태 · 라운드 20px — 4화면 동일
  • 칩 디자인 — 4화면 동일
  • 아이콘 굵기 · 스타일 — 4화면 동일

통제 실패 — 문맥 의존 상태

  • 탭 활성 상태 — 목록에서 비활성 탭이 활성처럼 표현
  • 하단 내비 유무 — 상세에서 지시 없이 제거됨
  • 상단 상태바 여백 — 화면마다 상이
  • 이미지 비율 — 10장 중 6차만 0.4745로 이탈
  • 한글 렌더링 정확도 — 차수별 파손·복구 반복

색·형태·간격 같은 정적 스타일은 완전히 통제됐지만, "지금 어느 탭이 활성인가" 같은 문맥 의존 상태는 통제되지 않았다. 이 경계가 정확히 사람이 개입해야 하는 지점이다.

17 · 후가공

고칠 것은 글자 깨짐이 아니었다

#화면처리
1홈비율 864×1821 → 1024×1821 (9:16) 가장자리 복제 확장 · 완료
2홈"4주 전" 숫자·단위 서체 규칙 통일
3목록비활성 홈 탭을 회색 #737B87로 덮기
4상세삭제 버튼 경고색 처리 — 파괴적 동작인데 신호 약함
5입력폼상단 상태바 여백 추가
6입력폼저장하기 버튼 하단 여백 확보
7입력폼우상단 저장 중복 버튼 제거

더 빈번한 문제는 논리 결함이었다

배지와 그래프의 추세 모순, 데이터 왜곡, 활성 상태 중복 표현 — 모두 시각적으로는 자연스러워 보이지만 UX상 오류다.

글자 깨짐은 눈에 띄어서 잡히지만, 이런 결함은 육안 검수로만 잡힌다. 생성물 검증에서 실제로 중요한 것은 후자였다.

한편 5차의 체종 파손 사례는 수정하지 않고 비교 이미지로 보존했다. "프롬프트로 텍스트를 통제할 수 없다"는 결론의 유일한 증거 자료이기 때문이다.

네 가지 설명할 수 있는가

① 프롬프트 구성 요소의 영향

추상어는 모델의 기본값을 호출한다. 스타일 토큰이 결과를 지배한다 — 6차에서 색만 바꾸자 레이아웃이 동일한데도 인상이 완전히 달라졌다. 페르소나는 스타일이 아닌 완성도에 작용한다.

② 문제점 식별과 수정

한글 파손은 확률적 현상이라 프롬프트로 통제할 수 없다. 텍스트 밀도와 파손률은 무관했다. 더 빈번하고 위험한 것은 글자 깨짐이 아니라 논리 결함이었다.

③ 일관성 유지 방법

텍스트 토큰 반복 삽입으로 정적 스타일은 완전히 통제됐다. 시드 고정과 토큰 고정은 목적이 다르다 — 전자는 재현, 후자는 이식이다. 문맥 의존 상태는 통제되지 않았다.

④ 협업 워크플로우

한 화면에서 토큰을 완성한 뒤 나머지에 이식한다. 동시에 개선하면 변경 원인을 특정할 수 없다. 홈에 6차수, 나머지 3장에 각 1차수를 투입한 것이 그 결과다.
